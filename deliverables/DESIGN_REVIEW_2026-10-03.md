# 全体設計レビュー（2026-10-03）

## 結論

**Solutionごとに1つのCMakeプロジェクトを生成し、依存順と実際のビルドをCMakeへ任せる方向は、現在の要件に合っている。公開APIを維持しながら、共有ビルドツリーに合わせて内部の責務を整理することを勧める。**

優先するのは、操作で使う構成の固定、表示とビルド参加の区別、生成ファイル・成果物・状態・ロックの管理単位の統一である。前回の5件の不具合のうち複数は、この境界が十分に表現されていないことと関係している。

この文書はレビュー結果と改善案であり、仕様変更の合意や修正実装を意味しない。最新の合意は[API設計](API_DESIGN.md)冒頭と[設計整理メモ](DESIGN_NOTES.md)の2026-10-01実装節を優先する。

## 対象と確認方法

- `cppbuild/`の管理・保存・依存解決・CMake生成・操作・観測状態・移動・テンプレート・イベント・環境判定を確認した。未コミットのCMake統合変更に加え、それと接続する既存実装も対象にした。
- 前回のコードレビューでは、Windows上のVS2022・VS2026・Ninjaの実ビルドを含む既存179件が成功した。実行環境の中断後、完了済み153件をログで確認し、残り26件を実行した。skipなし。
- 今回は設計確認のため、Ninja＋MSVCで小さな実行ファイルをビルドし、出力先変更時の観測状態と、Solutionの操作ロックを保持した状態でのProject.cleanを追加確認した。ビルドは成功。成功したビルドの警告一覧は別途採取していない。
- 今回、製品コードと既存テストは変更していない。全件テストの再実行、Linux/macOS、VS IDEのGUI、実際に複数プロセスを競合させる試験は行っていない。

## 維持する設計

| 設計 | 評価と理由 |
| --- | --- |
| Solution単位の構成、Project単位のターゲット操作 | 全体／個別の成果物共用を素直に表現できる。全体.slnを別途組み立てる処理や、Python側のビルド順制御を減らせる。個別操作でも全体を構成するコストは、合意済みのトレードオフとして扱う。 |
| 生成CMakeと非保存ビルド設定の分離 | 配布する生成ファイルを環境に依存させず、CppBuildを使わない構成・ビルドにも対応できる。初期キャッシュは操作用の生成物であり、管理設定の保存・復元元にしない方針を維持する。 |
| GUIDによるProject識別 | 名前・配置と依存の同一性を分離できる。最上位の参照一覧を優先する規則も、同梱された依存のコピーをそろえる目的に合っている。 |
| 管理設定のコピー取得、検証、競合検査 | `get()`のコピーと`save()`の明示、ファイル指紋の照合により、未保存の編集や古いインスタンスによる上書きを区別できる。 |
| 保存形式の相対パスと種類別ファイル | 移設条件を明確にできる。種類別ファイルを先に書き、参照する管理ファイルを置き換える方式は、保存途中の不整合を減らす。通常の失敗時の複数文書復元も実装されている。 |
| CMake File APIからの成果物取得 | Python側でEXE・LIB等の配置を推測する処理を減らせる。生成されたターゲットの情報を読み取る入口として継続する。 |
| cleanを生成経路から分離 | ソースや外部依存が使えなくても既存成果物をcleanできる。再生成しないことと対象外の成果物を残すことは、今後も独立して検証する。 |
| 部分成功と非同期実行の結果 | `FileOperationReport`でファイル変更済み・生成失敗を表せること、`RunReport.success`が未完了時に`None`になることは、利用側の誤判定を防ぐ。 |

## 優先度の高い改善

### 1. 共有ビルドツリーを、状態と排他制御の単位にもする

根拠：[engine.py](../cppbuild/engine.py)の`tree`・`generated`・`clean`、[solution_engine.py](../cppbuild/solution_engine.py)の`clean`、[information.py](../cppbuild/information.py)の`signature`、[workspace.py](../cppbuild/workspace.py)の`lock`。

ビルドツリーはSolution単位へ変わったが、生成・ビルドの観測状態はProjectの設定を中心に記録され、cleanのロックも個別と全体で異なる。

今回、次の動作を確認した。

1. Appのビルド後、`SolutionBuildSettings.intermediate_directory`だけを未使用の場所へ変更した。新しいツリーは存在しないのに、`info()`は生成状態・ビルド状態とも`current`を返した。
2. Solutionの`.cppbuild/operations`ロックを保持したまま、同じSolutionのApp.cleanを呼んだ。cleanは成功し、EXEを削除した。競合する実プロセスを動かした試験ではなく、同じ操作ロックで排他できていないことの確認である。

**改善案：** 操作開始時に、Solution・ビルドディレクトリ・生成環境・対象構成・Projectごとの有効設定を一つの内部データに固定する。全体／個別の操作で同じツリーを変更する場合は、共通のロックを使う。別ツリーでも共有の生成CMakeを書き換えるため、その書き込み範囲にも共通の排他が必要になる。

`info()`は引き続きディスク走査をしない。ただし、自分のAPIから分かるツリー変更や構成変更は状態へ反映し、観測済みの成果物をどのツリー・構成で得たかを保持する。全体生成成功を、異なる環境を指定した各Projectの個別生成成功と同一視しない。

### 2. 表示、要求形式、ビルド参加を別の項目で表現する

根拠：[graph.py](../cppbuild/graph.py)の`Node`・`resolve`、[workspace.py](../cppbuild/workspace.py)の`_requests`・`_display`・`external_requests`、[cmake_files.py](../cppbuild/cmake_files.py)の`_requested_types`・`_library`。

現状は、`STATIC`・`SHARED`などの形式と`DISPLAY`を同じ要求リストに入れている。また、依存ノードはGUID＋形式で識別する一方、表示判定はGUID単位である。表示専用Projectの依存も要求リストへ入り、通常のビルド参加へ変わる不具合につながっている。

**改善案：** Projectの同一性、形式ごとのターゲット、構成に含める理由、既定ビルドへの参加を分ける。少なくとも「必要な形式」と「表示のみか」は別の情報として持たせる。表示対象の構成可能性を検査する既存の制約は維持し、表示対象の依存が必要であることと、それを既定ビルドで作ることを区別する。

同様に、`INTERFACE_LIBRARY`の個別buildは「自分自身のコンパイルがない」ことと「依存先をビルドしなくてよい」ことを区別する。実体を持つ依存ターゲットも要求対象に含め、依存順序はCMakeへ任せる。実際に要求した処理と確認できた成果物に基づいて成功状態を記録する。

### 3. 名前と出力領域の規則を一か所で決める

根拠：[cmake_files.py](../cppbuild/cmake_files.py)の名前生成と`OUTPUT_NAME`、[workspace.py](../cppbuild/workspace.py)の`check`・`cache_script`、[output_paths.py](../cppbuild/output_paths.py)、[templates.py](../cppbuild/templates.py)の`_copy_tree`。

管理上のGUID、CMakeのターゲット名、ALIAS、成果物名、IDE表示名には、それぞれ異なる一意性の条件がある。現在の検査は基本ターゲット名と共有ライブラリ名を中心にしており、実行ファイルの共通出力先との衝突を捉えていない。指定成果物領域では、パス算出と所有マーカー作成も分離したままである。

**改善案：** 生成前に、作るターゲット・ALIAS・出力先を一覧にして検査する。人が読む名前は維持し、衝突する場合の規則を明示する。特に、同じ名前の実行ファイルを別Solutionで許す場合は、成果物のディレクトリまたは名前を区別する必要がある。DLL名の衝突は既存の拒否規則を維持し、ディレクトリを分けるだけで解決した扱いにしない。

生成物領域は「場所を計算する」「所有を確認して確保する」「走査・テンプレートから除外する」「clean対象を特定する」まで同じ規則を使う。外部から取り込む既存ライブラリの所有権とは分ける。非保存の出力先設定を管理JSONへ保存する必要はない。

### 4. 生成するファイル一式を確定してから書く

根拠：[workspace.py](../cppbuild/workspace.py)の`Plan`・`documents`・`write`、[cmake_files.py](../cppbuild/cmake_files.py)の`write`、[storage.py](../cppbuild/storage.py)の`publish_documents`。

`Plan`は可変のSolution／Projectを参照する。`documents()`の途中でリンク先を再度`plan()`し、追加の設定読み込みとソース走査を行うため、解決・検証・生成内容の確定が明確な段階になっていない。リンク先の独立利用に必要なCのファイルが書かれない問題も、主操作で必要な範囲と、単独利用のために出力する範囲の違いに関係する。

また、生成ファイルは順番に書く。後半で手書きのCMakeListsとの衝突が見つかると、それ以前の生成ファイルだけ更新され得る。ファイル単体のatomic writeと、ファイル一式の整合性は別の保証である。

**改善案：** 読み込んだ管理設定とソース一覧を操作内で固定し、次を先に確定する。

- 今回構成するProjectと依存。
- リンク先の単独利用まで保証するために生成するファイルと、その参照先。
- 変更予定の全パス、所有確認、ロック対象。
- 各ファイルの完成した内容。

その後に衝突を一括検査して公開する。通常の書き込み失敗時の復元には既存の`publish_documents`を活用できる。強制終了や電源断まで含む完全なトランザクションは、今回の提案の前提にしない。

リンク先の独立利用用ファイルを生成できない場合は、理由と対象を結果に残す。合意済みのリンク先への書き込み方針は維持し、その範囲と成功条件を明確にする。

## その次に整理する設計

### Pythonと生成CMakeの判断を一致させる

形式選択は[core.py](../cppbuild/core.py)の`_resolved_build_settings`、[graph.py](../cppbuild/graph.py)、[cmake_files.py](../cppbuild/cmake_files.py)の`_library`にまたがる。CppBuildなしでも形式を切り替えられるため、PythonとCMakeの両方に判断が必要な点は避けにくい。

選択の優先順位と結果を小さな表で定義し、同じ入力についてPython経由と素のCMakeで、生成される形式・リンク対象・成果物が一致することを検査するとよい。Pythonの今回の選択結果を配布用CMakeへ埋め込む方式へ戻さない。

`CMakeLists.txt`と`CppBuildTopLevel.cmake`の役割、`CPPBUILD_REQUEST_*`等の変数の範囲、対応する生成形式の版も短く文書化する。今後この取り決めを変更するときは、古い生成ファイルとの混在を検出できるようにする。

### 設定の適用範囲を明確にする

公開APIの`get/save/reload`と`set_build_settings`の分離、後者の全置換は維持できる。ただし、同じ設定クラスの中でも効く範囲が違う。

| 範囲 | 例 | 整理の方向 |
| --- | --- | --- |
| 構成するツリー全体 | 生成器、コンパイラ、アーキテクチャ、GoogleTestの取得元 | 個別Projectから指定しても、どのツリーを構成するか、どの値が共通になるかを明示する。 |
| ターゲット | 形式、C++規格、成果物ディレクトリ | 解決済みのProject設定として保持する。 |
| 今回の操作 | Debug／Release、対象選択、並列数、実行引数、待機 | 生成定義から分離し、操作開始後は固定する。 |

`external_build_settings`は`SolutionBuildSettings`全体を受け取るが、利用側で有効な設定範囲はその全フィールドと同じではない。内部では必要な値に絞り、利用手順に対応項目を示すと誤解が減る。公開型の変更は互換性を検討してから行う。

### ファイルを増やすより、境界を明確にする

現在の規模では、汎用プラグイン機構や大規模なクラス階層を導入する理由は薄い。次の小さな整理で効果が見込める。

- `graph`は固定した設定から依存を解決し、生成器の呼び出しや状態更新は操作側で行う。
- `cmake_files`は完成した生成用データから文字列を作り、追加の設定読み込みを要求しない。
- `engine`は操作順序を扱い、File APIの読み取りと生成器別cleanの詳細は独立した関数群へまとめる。
- `ProcessReport`等の共通結果型と低水準のプロセス実行を、上位の操作モジュールから切り離す。現在の`tooling → engine → tooling`、`execution → engine → execution`という相互参照を減らせる。
- CMake文字列の出力形式だけを理由に、新しいテンプレートエンジン依存を追加する必要はない。

### 生成器への依存と性能は、根拠を持って改善する

VSの直接CleanとNinjaのオブジェクトディレクトリ削除は、既存要件を守るための実装選択として理解できる。ただし生成器固有の知識を含むため、生成器別の処理としてまとめておく。単一構成生成器やXcodeを増やす際に、現在の「VS以外はNinja」という分岐を点検する。

File APIは`target_data()`ごとにモデルを読み直している。`documents()`もリンク先の計画を再計算する。まず操作内で結果を共用するとよい。今回、規模を増やした性能計測はしておらず、具体的な高速化率や常時キャッシュの必要性は判断していない。

## テスト設計

実ビルドと、`.cppbuild`を外して移設先で素のCMakeを実行する試験は、要件を直接確認している。この方向は維持する。

一方、機能単独の成功に加え、機能を組み合わせても守る条件を増やしたい。例えば出力領域の既存テストは、内部の`output_paths.claim()`でマーカーを先に作っているため、公開APIからの実ビルドがマーカーを作らない不具合を検出できなかった。

追加する回帰試験は、次の観点を優先する。

1. 表示専用Projectと、その推移的依存が既定ビルドへ混入しない。
2. 別Solutionの同名Projectでも、ターゲット名・成果物・CTest対象の衝突規則が守られる。
3. ヘッダーの有無にかかわらず、インターフェースProjectのbuildが必要な依存を作る。
4. 公開APIで指定成果物を生成した後、再open・走査・テンプレート・cleanで所有範囲を守る。
5. 利用側が使わないProjectにも外部依存があるリンク先を、生成ファイルだけで単独構成できる。
6. 全体／個別で同じツリーのロックを共用し、ツリー変更が観測状態へ反映される。
7. 生成前の衝突・書き込み失敗で、どのファイルまで変わるかが定義どおりになる。
8. 形式選択の同じ組み合わせを、Python経由と素のCMakeで比較する。

全組み合わせを網羅する大きな試験群より、各条件を破る最小の構成を使う。OS・生成器を変えたときに影響する試験だけを広げる。手元で検証する既存方針を維持し、Linux/macOSと最小対応CMake版の確認は未実施として管理する。

## 資料の整理

現行資料に、最新の追記と撤回済みの本文が混在している。[API_DESIGN.md](API_DESIGN.md)には実装済みの新方式の前に「実ビルド検証は未着手」があり、[BUILD_DESIGN.md](BUILD_DESIGN.md)には旧Project別ツリーの状態管理が残る。最新のAPI節にも、現在の実装と異なる`--target clean`の記述がある。

優先する節を読み分ければ判断できるが、利用者と将来の実装者が仕様を取り違えやすい。現行の入口・範囲・戻り値・制約を本文へまとめ、旧仕様と採否の経緯は履歴として参照できる形にするとよい。過去の記録自体は書き換えずに残す。
