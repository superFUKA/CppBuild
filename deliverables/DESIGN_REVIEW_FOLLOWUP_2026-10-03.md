# 実装後の設計レビュー（2026-10-03）

## 結論と対象

**Solution単位のCMake構成、Project単位の操作、GUIDによる依存解決、非保存設定を初期キャッシュで渡す方針は、現在の要件に対して妥当である。公開APIの大幅な変更より、操作で使うデータと状態の管理単位をそろえることを優先したい。**

対象は `6979cf6` と周辺実装。依頼に合わせ、動作よりも責務・データの流れ・APIの意味を中心に静的レビューした。製品コードの変更、テスト・実ビルドの実行、並行処理の再現は行っていない。以下の具体例はコード経路に基づく指摘であり、今回実行して確認した結果ではない。前回の195件成功は既存記録である。

前回レビューの4項目は改善している。ただし「設定の固定」「状態の管理単位」「生成できなかった範囲の報告」は残っている。提案は仕様変更の合意を意味しない。

## 1. 優先度：高 — Planの内容が、操作を通して固定されていない

根拠：`workspace.py` の `plan`、`Plan._documents`、`Plan.lock`、`Plan.cache_script`、`engine.py` の `configure`。

- `graph.resolve` はノードのビルド設定をコピーする一方、Planは可変のSolution・Projectを保持する。
- `Plan.lock` はロック対象を知るため、ロック取得前に `_all_documents` を評価する。その途中でリンク先を再度 `plan()` し、設定を読み込み、ファイルを走査する。
- 文書だけはキャッシュされるが、その後の `cache_script` はProjectから設定を再解決する。構成先の中間ディレクトリもSolutionから読み直す。
- 管理設定の保存ロックは `.cppbuild/.write.lock`、操作ロックは `.cppbuild/operations/.write.lock` であり、操作ロックだけで設定の不変性まで保証する構造ではない。

このため、「依存解決で使った設定」「生成した文書」「初期キャッシュ」「結果として記録した設定」が同じ時点のものか、処理全体を追わなければ判断できない。`cached_property` の導入は生成文書の再計算を防ぐが、操作全体の固定にはならない。

**改善案：** 読み込んだ管理設定、解決済みのビルド設定、ソース一覧、出力文書、対象ツリーを、操作内の確定データとしてまとめる。実行段階はそのデータだけを参照する。出力先を確定してロックした後に読み込み元の版を再確認し、変わっていたら競合として返す。通常の設定保存をビルド完了まで禁止する必要はなく、「今回使った版」と「現在の版」を区別できればよい。

巨大な新クラスや全設定オブジェクトの不変化は不要。まず `cache_script` と状態記録が、ノードと同じ解決結果を使う形にそろえるのが小さな第一歩になる。

## 2. 優先度：高 — 状態の判定に、生成・ビルド・実行の設定が混ざっている

根拠：`information.py:34` の `tree_key`、同 `signature`・`snapshot`、`engine.py:239` の `in_tree`、`generators.py` の `Toolchain.identity/context`。

`signature` は `ProjectBuildSettings` 全体を生成状態・ビルド状態の両方に使う。そのため、実行引数や `run_wait`、テスト並列数だけを変えても、生成状態とビルド状態がともに `stale` になる。これらはCMake定義やバイナリーの内容を変えないため、利用者が読む状態の意味として不自然である。

また、実際のツリー識別は `Toolchain.context` と出力先から決まり、状態側は未解決の設定値を比較している。既定生成器の省略と同じ生成器の明示は別設定でも同じツリーになる。現在は「設定値が同じ」と「同じツリー」を `in_tree` で同一視しており、両者の目的が混ざっている。

**改善案：** 次の情報を分ける。

| 情報 | 管理する単位・内容 |
| --- | --- |
| 構成済みの状態 | ツリーの所在・解決済み生成環境・構成時に使った定義 |
| ビルド済みの状態 | ツリー・Project GUID・形式・Debug/Release・ビルドに影響する設定 |
| 最後の操作結果 | 実行引数、待機、並列数、終了結果など |

`info()`でツールを起動しない条件は維持できる。解決結果は操作時に記録し、未解決の設定変更は「変更を検知した」こととして扱う。設定値の比較を、実際のツリー同一性を表す名前で使わないことも重要である。

全構成の履歴を保持する大きなキャッシュは必須ではない。直近の観測だけでも、何を構成・ビルドした記録かを明示すればよい。

## 3. 優先度：高 — 全体／個別操作で、対象決定と状態記録が重複している

根拠：`engine.py:279`、`solution_engine.py:55`、`solution_engine.py:96`、`testing.py:55`。

ProjectとSolutionのAPIが分かれていること自体は自然。しかし内部でも、構成・対象の決定・ビルド・成果物取得・状態記録をそれぞれ実装しており、同じルールの修正が別経路へ反映されにくい。

具体的に、ProjectのbuildはINTERFACE_LIBRARYも扱えるよう依存の閉包からビルド対象を作る。一方、Solutionの明示選択では選択したルートだけから対象を作る。ファイルを持たないインターフェースだけを `build_projects` に指定すると、ビルドコマンドを省略する経路があるにもかかわらず、依存の閉包に対するビルド済み記録へ進む。同じ「指定Projectをビルドする」という意味を共通処理で表せていない例である。

cleanにも同じ問題がある。Solution.cleanはSolutionの設定でツリー・構成を選ぶが、結果を各Project自身の設定で記録する。SolutionがDebug、ProjectがReleaseを選ぶ場合、削除対象と記録対象の構成が一致することを保証していない。依存解決をしないcleanの方針は維持しつつ、操作対象と記録には同じ確定値を使うべきである。

**改善案：** 公開の入口は残し、内部の「選択したProjectから実行対象を決める」「実際に操作した対象へ結果を記録する」を共有する。操作データにツリー・構成・ターゲット・観測対象を持たせる。cleanの対象を依存の閉包まで広げる必要はない。ビルドとcleanで異なる対象規則を明示し、結果記録の方法を共通化する。

最初に対象計算と結果記録を小さな関数へ切り出せばよく、全操作を一つの巨大な関数に統合する必要はない。

## 4. 優先度：中 — 本操作の成功と、リンク先の単独利用の準備が区別されていない

根拠：`workspace.py:132` の `Plan._documents`。

リンク先の単独利用用ファイルは、依存解決に成功したときに追加で生成する。`OSError`・`SettingsError` は捕捉して処理を続けるため、本操作は成功しても、一部のリンク先は単独構成できないままになる。これは設計整理メモで明示的に見送った事項であり、今回初めて判明した回帰ではない。

問題は、任意の追加処理をすることより、その完了範囲が結果から分からないことにある。また「全部書くか何も書かない」の対象は、収集できた文書だけであり、要求した全Solutionの生成完了を意味しない。

**改善案：** 本操作に必須の生成範囲と、リンク先の単独利用の準備を、計画・結果で分ける。後者を実施できなかった対象と理由を保持する。まず内部の生成結果に診断を残し、公開結果への追加は互換性を検討する。公開結果型の変更を理由に、内部でも理由を捨てる必要はない。

通常の書き込み失敗時に復元する現在の方針は、この規模では妥当。プロセス強制終了や外部CMakeからの同時読み込みまで含む一括公開は、別の保証として扱えばよい。

## 維持したい設計と、急がなくてよい整理

- **Solutionの1ツリーとCMakeへの依存順委譲：** 全体／個別の成果物共用という要件を直接表している。
- **入口と最上位用CMakeファイルの分離：** 所属Projectの定義と、利用側の視点による依存解決を分ける理由がある。
- **保存設定と非保存設定の分離：** 配布用CMakeに個人のビルド環境を混ぜず、単独利用を可能にする方針として自然。
- **Requestのbuilt/listedの区別：** 表示とビルド参加をPython側で表した改善は妥当。CMakeへ渡すときに文字列リストへ変換すること自体は問題ではない。
- **名前の事前検査：** 素のCMakeで形式を変える要件があるため、今回使用する形式以外も検査することには理由がある。将来はターゲット名・別名・出力名の確定と検査を同じデータから行うと追いやすい。
- **生成器別clean：** 再生成禁止と単一Projectのみの削除を守る実装上の理由がある。生成器追加時に処理を分ければよく、現時点で汎用プラグイン機構は不要。

設定クラスの項目は公開APIとして維持してよい。内部ではツリー全体の設定、ターゲットの設定、今回の操作設定に分けて使うと、継承・競合条件・状態への影響が明確になる。

## 推奨する順序と確認観点

1. 操作で使う解決済み設定と対象を固定し、初期キャッシュ・実行・状態記録へ共通に渡す。
2. 全体／個別で対象計算と結果記録を共有する。INTERFACE_LIBRARYの明示選択、構成が異なるProjectを含むcleanを確認する。
3. 生成・ビルドの状態判定から実行専用設定を分け、操作時に観測したツリーと構成を記録する。
4. リンク先の単独利用準備について、未完了の対象と理由を結果へ残す。

追加確認は、実行引数だけの変更、生成器の省略／明示、計画後の設定変更など、上記の境界を確認する小さな試験を優先する。今回はレビューまでであり、修正・回帰試験追加・全件再実行は未実施。
