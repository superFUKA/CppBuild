# APIの情報受け渡しの点検とOSS実装の調査

> 本資料は調査時点の記録。現在のクラス分担・API・合意状態は [API_DESIGN.md](../deliverables/API_DESIGN.md) を参照。以下の旧APIや設定ファイルの入口を現行仕様として扱わない。

調査日：2026-09-11。API_DESIGN.mdの11ジャンル全体を対象とした。

共通設定ファイルとテンプレートはプロジェクト管理のための合意済みの入口とする。それ以外の情報を渡すためだけに、利用側へファイルの作成・保存形式の遵守を要求しない。ベストプラクティスは目的への適合性を評価して取り入れる。

## 1. 点検結果と今回の修正

別のJSON等を利用側に書かせるAPIは見つからなかった。ただし、一時的なビルド構成を渡す経路が不足しており、保存済みプロファイルの登録を経由する必要があった。この間接的な保存の強制を修正した。

| ジャンル | 点検結果 | 対応 |
| --- | --- | --- |
| 1 基本操作 | openは共通設定ファイル、createは出力先とテンプレートを扱う。合意済みのファイル利用 | 維持。ルート引数や削除APIを復活させない |
| 2 テンプレート | ディレクトリ＋設定ファイル、ファイル用テンプレートの登録は合意済み | 維持。登録の取得・変更は構造体で行う |
| 3 設定・情報 | 設定を構造体で受け取るため、専用ファイルを作らせていない | 維持。共通設定への保存と、受け渡し方式の問題を区別する |
| 4 ファイル操作 | 実際に操作するパスと、登録済みテンプレート名を受け取る | 維持。ファイル操作が目的なのでパス指定に理由がある |
| 5 CMake更新 | 保存済み構成の名前しか指定できなかった | BuildSelectionに構成データの直接指定を追加 |
| 6 依存・リンク | 準拠プロジェクトは共通設定ファイル。外部依存はパッケージ情報・ソース場所・バイナリ情報を構造体で受け取る | 維持。外部依存に独自設定ファイルの作成は要求しない |
| 7 ビルド・実行 | 一時的な出力先・ジェネレーター等の指定に事前登録が必要だった。検査に使ったツールを実行へ渡す経路も弱かった | BuildSelectionとRuntimeEnvironmentを追加 |
| 8 テスト | 実行構成が保存済みプロファイルに依存していた | 構成値の直接指定を追加。テスト構成用テンプレートはファイル利用が自然なので維持 |
| 9 PCH | ヘッダー一覧を直接指定できる。まとめヘッダー生成は任意 | 維持。PCH設定を渡すための設定ファイルは不要 |
| 10 環境チェック | 検査条件はデータだが、Project版の構成は名前のみ | 直接構成と実行時環境を受け付け、実行APIと同じ指定を使えるようにした |
| 11 イベント | 関数・コールバックで登録し、結果もデータ | 維持。イベント定義ファイルやコールバックのコマンド化を必須にしない |

### 構成を保存せず実行する例

```cpp
BuildProfile temporary;
temporary.buildDirectory = "out/experiment";
temporary.generator = "Ninja";
temporary.defaultConfiguration = "Debug";
temporary.cmakeCacheVariables = {{"MY_FEATURE", "ON"}};

ExecutionOptions execution;
execution.runtime.cmakeExecutable = "C:/tools/cmake/bin/cmake.exe";

auto result = project.build({.profile = temporary}, execution);
// setBuildProfile、saveSettings、追加設定ファイルの作成は不要。
```

パスは例であり、そのツールが環境に存在することは確認していない。実行はCMakeCache等の内部ファイルを更新し得るが、共通設定ファイルへ一時構成を登録しない。

保存する設定の変更APIは、従来案の自動保存をいったん維持した。利用側にファイル化させるAPIではないため、一律に撤去する理由はない。一時的な操作オプションと分けた上で、保存タイミングはジャンル3のレビューで引き続き検討する。全ターゲット設定のメモリ上だけの変更APIを今回追加するところまでは行っていない。

## 2. 参考にしたOSS

公式ドキュメントと公開ソースを確認した。以下はライブラリの直接採用や依存追加を決める比較ではなく、設計・実装方法の比較。参照したmain/master/develop2は移動するため、実装を取り込む段階ではコミットを固定して再確認する。

| 実装 | 確認したこと | 今回への適用判断 |
| --- | --- | --- |
| Rust cmake-rs | Configに対してdefine、env、out_dir等を呼び、ビルド設定を組み立てる。configure/buildの追加引数も受け取る。[API](https://docs.rs/cmake/latest/cmake/struct.Config.html) | 値を直接渡す方式を参考にする。Cargo向けの既定値をこのライブラリの標準にはしない |
| scikit-build-core | CMakerは構成・ビルドを別メソッドとして持ち、マッピングで設定を受け取る。内部で初期キャッシュファイルの生成やFile API応答の読み込みを行う。[実装](https://raw.githubusercontent.com/scikit-build/scikit-build-core/main/src/scikit_build_core/cmake.py) | データAPIと内部ファイル処理の分担を参考にする。Pythonパッケージ作成の構造を必須にしない |
| Conan 2 CMake helper | configureへ辞書・追加引数・出力先、buildへターゲットやビルドツール引数を渡せる。生成済みPresetsを読む構造も持つ。[API](https://docs.conan.io/2/reference/tools/cmake/cmake.html)、[実装](https://raw.githubusercontent.com/conan-io/conan/develop2/conan/tools/cmake/cmake.py) | 工程ごとの引数と出力経路を参考にする。Conanのrecipe・toolchain・Presets一式を利用条件に持ち込まない |
| VS Code CMake Tools | File APIドライバーが問い合わせを作成し、成功したconfigure後やbuild後にコードモデルを更新する。[実装](https://raw.githubusercontent.com/microsoft/vscode-cmake-tools/main/src/drivers/cmakeFileApiDriver.ts) | 成果物情報や更新状態を内部で管理する参考。VS Codeに依存する公開APIにはしない |
| python-cmake_file_api | 作者が単独のFile APIアクセス例として公開。Cmakeクラスと情報表示用の例を掲載している。[リポジトリ](https://github.com/scivision/python-cmake_file_api) | 小さな参考例として位置付ける。実装ファイルの取得ができなかったため、詳細設計・品質の根拠には使わない |

Conanの取得ソースは行が圧縮された表示であり、詳細の参照には公式APIドキュメントを併用した。scikit-build-coreのAPIページを取得できなかった箇所は公開ソースで補った。

## 3. 調査から得た改善点

### A. 今回のAPI案へ反映したもの

**保存済み構成と、今回だけの構成を両方受け付ける。** cmake-rsの設定オブジェクトやscikit-build-coreのデータ引数は、設定値を直接扱える実例。BuildSelectionを未指定／名前／構成値の選択とした。直接値は登録・保存せず、その操作に適用する。名前との暗黙のマージはせず、必要なら利用側が取得済み構成をコピーして変更する。

**ツールと環境を子プロセス単位で渡す。** cmake-rsには子プロセス環境を指定するAPIがあり、scikit-build-coreも環境データを実行へ渡している。RuntimeEnvironmentを検査と実行で共有できる型として追加した。実行のたびに親プロセスのPATHを書き換えたり、環境設定ファイルを生成したりする必要を減らす。アプリ固有の環境上書きは事前ビルドに適用しない。

**一時指定の後に残るキャッシュを考慮する。** scikit-build-coreやcmake-rsの実装には既存ビルド状態との不整合を扱う処理がある。一時引数を保存しなくてもCMakeキャッシュは残るため、本案にも有効構成の比較と再構成・診断の必要性を明記した。別構成を実行するときに前回値が無条件に消えるとは扱わない。

### B. 改善候補として残すもの

| 候補 | 改善する場面 | 判断 |
| --- | --- | --- |
| CMakeキャッシュ値の型を保持する | 現在のmap<string, string>ではBOOL・PATH・STRING等の区別を表現しにくい | bool・パス・文字列等の型付き指定が有力。CMakeのリスト表現やWindowsパスを含めて設計してから追加 |
| 構成更新の内部処理を分ける | updateは走査・入力生成・configureをまとめている | 内部を分けて失敗工程・再実行範囲を管理する。利用側の簡単なupdateは残す。公開関数を一律に増やす必要はない |
| CMake File APIによる成果物情報の型付き取得 | 実行対象のパスや構成、ターゲット一覧を利用側が必要とする | 生成後の情報取得に使用し、ProjectInfoへ型付きで返す。生JSONファイルを利用側に解析させない。未取得・古い・取得失敗を区別する |
| 高度な引数の追加経路 | 基本構造体に未対応のCMake機能が必要になった場合 | configure/build/ビルドツールの工程別に文字列一覧を受ける案。既存の型付き指定との衝突処理を決めてから追加 |
| 変更のない生成ファイルを再書き込みしない | updateを繰り返しただけで不要な再構成が起きる場合 | 内容比較などを内部実装で行う候補。公開APIの追加は不要 |

型付きキャッシュの参考はscikit-build-coreのinit_cacheと_compute_cmake_args、工程別引数の参考はConanのconfigure/buildである。成果物情報更新の参考はCMake ToolsのFile APIドライバー。生成ファイルの同一内容判定は、これらの実装に共通すると断定したものではなく、本プロジェクトのupdate頻度からの設計判断。

### C. そのまま採用しないもの

- **ビルドの既定対象をinstallにすること。** cmake-rsのbuild_targetの既定はinstallだが、このライブラリは作成したプロジェクトの開発操作が目的なので、通常のビルドを維持する。[API](https://docs.rs/cmake/latest/cmake/struct.Config.html)
- **失敗時に呼び出し側ごと停止させること。** cmake-rsのソースにはpanicによる失敗処理がある。ビルドスクリプト向けの選択として理解できるが、本ライブラリはアプリが判断できる結果・診断を返す。[実装](https://raw.githubusercontent.com/rust-lang/cmake-rs/master/src/lib.rs)
- **不整合時にキャッシュやビルドディレクトリを無条件に消すこと。** 参考実装には自動クリーンの処理があるが、本案では異なるツール設定・場所との不整合を診断し、利用側が別の出力先などを選べるようにする。
- **全設定を外部形式へ寄せること。** パッケージング用の設定ファイルやPresetsを使う実装があっても、このライブラリのAPI利用のためにそれらをすべて要求しない。
- **テンプレートを全部メモリ上の文字列へ置き換えること。** 利用側のファイル化を避ける原則は、合意済みのテンプレート管理まで撤回する理由にならない。
- **対象ディレクトリの再走査をなくすこと。** 現在の目的は、指定配下を管理・表示して更新すること。CMake側へ渡す一覧の作り方を改善しても、この操作は維持する。

## 4. 残る設計上の注意点

一時的なBuildProfileを渡す道はできたが、CMake用ファイルの保存位置、異なる構成の切り替え、キャッシュ値の削除・リセット方法は具体化が必要。同じビルドディレクトリを複数操作が同時に更新する設計にはしない。

設定変更APIの即保存は、今回の受け渡し違反とは別問題としてまだ提案段階。プロジェクト構成を永続的に変える操作と、一時的に試す操作をすべて同じ保存規則にしない。

今回確認したOSSのいずれか一つが本ライブラリの全要望を満たすとは判断していない。用途別の実装から必要な部分を参考にする。実行・ベンチマーク・全テスト・依存導入の評価は行っておらず、ドキュメントと公開コードによる設計調査である。
