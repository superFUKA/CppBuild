## 共通構成

PythonライブラリとしてCMakeをラップする。プロジェクト作成もCMakeを利用する前提。利用側に、APIで渡せる情報を専用ファイルへ書き出すことは要求しない。

| オブジェクト・型 | 役割 | 状態 |
| --- | --- | --- |
| Project | 一つのプロジェクトと所属Targetを管理し、更新・ビルド等を行う | 確認済み |
| Target | 一つの論理的なビルド対象。対応種類を複数持ち、ファイル追加・削除・移動を行う | 確認済み |
| project.settings | 全体設定の取得・変更・保存・再読み込み | 確認済み |
| target.settings | ターゲット固有設定の取得・変更・保存・再読み込み | 確認済み |
| ProjectSettings / TargetSettings | 上記設定管理クラスの名前 | 再提案 |
| ProjectSettingsData / TargetSettingsData | get()で返す独立した設定値のコピー | 再提案 |
| TemplateTools | プロジェクトからテンプレートを作成 | 確認済み |

### 保存場所とパス

- 全体設定は `.cppbuild/project.json` を入口とし、必要なら分割する。素材は `.cppbuild/templates/` に保存する（確認済み）。
- ターゲット設定は各ターゲットのディレクトリに置く。ファイル名・下位ディレクトリは未決定。全設定をプロジェクト直下へ集約しない（確認済み）。
- `Project.open(config_directory)` に渡すのは `.cppbuild` ディレクトリ。必要な設定と所属Targetを自動で読み込む（確認済み）。
- Targetのadd_file／remove_file／move_fileに渡す相対パスはターゲットディレクトリ基準（確認済み）。
- Project操作と全体設定内の相対パスはプロジェクトルート基準。open/create等の入口は呼び出し側の作業ディレクトリ基準（確認済み）。
- 今回の整理：Target固有設定のソース・出力先・実行時作業ディレクトリ、およびtarget.settingsのリンク先などのファイルシステム相対パスはターゲットディレクトリ基準とする。全体設定内のTarget参照・共有プロファイル内のパスはプロジェクトルート基準。optionsで渡すパスも、対応する設定項目と同じ基準を使う。テンプレート名・パッケージ名・システムヘッダー名はファイルシステム相対パスとは区別する。

### 設定と自動更新

確認済み：getはコピー取得、saveは検証・保存・反映、reloadは保存済み設定の読み直し。設定操作だけでCMake再生成・ビルドは行わない。保存失敗時にメモリだけ新設定へ切り替えない。

確認済み：add_file・remove_file・move_fileは `auto_update=True` が既定。Falseでもファイル操作と管理情報更新は行い、CMake反映だけを保留する。公開scan APIは設けない。updateは走査とCMake再生成まで行い、コンパイルしない。

今回の整理：未反映状態はTargetごとに区別し、Projectは全体設定の未反映状態と各Targetの状態を集約する。Targetの更新成功で他Targetの未反映状態を消さない。保留変更は対象のupdateまたは次のbuildで反映する。ファイル操作のauto_updateは操作したTargetの保存済み設定とビルド用CMakeを使う。処理の直列化・並行実行の詳細は未確定。

### 結果・失敗の扱い（詳細は再提案）

| 型 | 主な情報 |
| --- | --- |
| ChangeReport | 作成・変更・削除パス、診断、CMake反映が必要か |
| UpdateReport | 成功可否、認識ファイル、CMake実行結果、ビルドディレクトリ |
| FileOperationReport | ファイル変更、更新の有無と結果、全体の成功可否、未反映状態 |
| LinkReport | 依存の識別子・対象ターゲット・選択種類・変更内容 |
| ProcessReport / OperationReport | 終了コード、出力、実行工程、成功可否 |

Pythonでは不正な引数・設定・入出力失敗は例外、起動した外部プロセスの非ゼロ終了は結果の成功可否で示す案。部分的に完了した変更を結果・例外に残す。ファイルだけ作成できCMake更新に失敗した場合を成功扱いにしない。具体型は未確認で、旧C++風のResult型をそのまま要求しない。

ログ通知・キャンセル・ツールパス・子プロセス用環境変数は実行時データで受け取る案。これらの事前保存を必須にせず、親プロセスの環境を書き換えない。

| API | 用途・戻り値 | 状態 |

| Project.create(destination_directory, project_name, *, template=None) | プロジェクトを作成しProjectを返す。任意のtemplateで既存テンプレートを選ぶ | project_type削除・template指定を確認済み |

| project.remove_target(name) | 所属登録を解除。ソース・ターゲット設定ファイルは残す | 基本合意 |

最新の合意：`Project.create` の `project_type` は不要とし、実行ファイル・静的ライブラリ・共有ライブラリ等の種類はターゲット側で指定する。ProjectTypeとTargetTypeを二重に指定する以前の案は採用しない。他の基本操作APIと、主ターゲット・参照中ターゲットの解除を制限する方針は基本合意とする。

確認済み：template省略時の `Project.create` は空のプロジェクトを作成し、main_targetは未設定（None）とする。`add_target(directory, name, target_type, settings=None)` で最初に追加したTargetを自動的にmain_targetへ設定する。2個目以降の追加では変更せず、その後の変更はproject.settingsで行う。任意のライブラリが種類の登録だけで静的・共有の両方へ対応するとはしない。

確認済み：テンプレートからの作成は `Project.create(..., template=...)` という任意引数で指定する。project_typeへテンプレートを渡す以前の方式は採用しない。テンプレート参照型の名前とcreate_project_templateの具体的な戻り値型は引き続き検討する。テンプレートには複数のターゲット設定も含められる。template指定時はターゲット構成とmain_targetをテンプレートから引き継ぐ。

```python
template = TemplateTools.create_project_template(
    project=source_project,
    destination_directory="C:/templates/my_app",
)
project = Project.create(
    destination_directory="C:/work/NewApp",
    project_name="NewApp",
    template=template,
)
```

再提案：所属の変更はProject、個別の設定変更はTarget.settingsへ置く。独立したTarget.openや重複APIは当面増やさない。既存ターゲットの取り込みは必要性を確認する。主ターゲット・依存参照のあるターゲットの解除は、参照を解決するまでエラーにする案。

プロジェクト全体の削除・独立した復元APIは設けない。

### 一巡後の基本操作の整理（add_target・初期構成は確認済み）

Project.create／open、project.get_target／targets／add_target／remove_targetの6つを維持する。ユーザーの修正により、add_targetは追加に必須の名前と種類を直接引数で受け取り、settingsは任意とする。settings未指定時には既定の設定を用意する。呼び出し形は`project.add_target(directory, name, target_type, settings=None)`。設定データを必須にして名前・種類をその中だけで渡す直前の案は採用しない。

ターゲットが複数種類に対応できる既存方針は維持する。作成時の複数種類の指定形式、引数と設定データの重複・矛盾の検証、既定設定の具体的な値は実装時に整理する。

確認済み：template未指定のcreateは空のProjectを作成し、main_targetは未設定（None）とする。最初のTarget追加時に自動でmain_targetへ設定する。2個目以降の追加では変更せず、以後の変更はproject.settingsで行う。テンプレート指定時はターゲット構成とmain_targetを引き継ぐ。

remove_targetは所属登録のみを解除して実ファイルを残し、主ターゲットや参照中のターゲットは先に設定・リンクを変更してから解除する案。解除手順の詳細は引き続き再提案とする。

プロジェクトテンプレート作成はProjectのメンバーにしない。ビルド成果物を除外し、各ターゲット設定も含める。作成者にCMakeの知識・スクリプトの手書きを要求しない。作成時に反映する値はproject_nameのみで、任意の名前・コードを推測して変更しない。独自variablesや生成スクリプト登録を現要件に加えない。

確認済み：ファイルテンプレートはProjectで共有する。テンプレート素材の作成はproject.create_file_template、登録操作はproject.settings、テンプレートを使ったファイル追加はtarget.add_fileで行う。旧登録APIとの二重提供は前提にしない。inspect系の補助APIは今は必須にしない案。

### 対象外：ターゲット用テンプレート

単一ターゲットのテンプレート作成・利用は不要とする。`TemplateTools.create_target_template` や `project.add_target(..., template=...)` は設けない。プロジェクト用・ファイル用テンプレートは維持する。

種類を指定してターゲットの標準初期構成を用意することは別の機能として扱う。`project.add_target(directory, name=..., target_type=..., settings=None)`で名前・種類を直接受け取り、settings省略時は既定設定を使う。独自ターゲットテンプレートの登録・直接指定のどちらも前提にしない。TESTの構成を標準化する方針と、複数種類への対応は維持する。

確認済み：`project.info()` は設定に加えて処理結果等の保持情報を取得する用途で残す。設定値のみを返すsettings.getと区別し、認識済みファイル一覧、取得済みの成果物パス、更新・ビルドの状態や診断等をまとめて返す。情報取得のための走査・CMake実行は行わない。未取得や古くなった情報を最新の結果として扱わないよう、状態・取得時点も示す案。取得できる詳細項目は引き続き設計する。

再提案：ProjectSettingsDataは名前・main_target・所属ターゲット参照・ビルド構成・テンプレート登録を持つ。TargetSettingsDataは名前・対応種類・種類別設定・ソース配置・公開ヘッダー・コンパイル設定・リンク・PCH等を持つ。各saveは自分の範囲のみを変更し、Project側の古いコピーでTarget設定を上書きしない。所属一覧の変更はadd/removeへ委ね、saveで無検証に差し替えない。

確認済み：main_targetはproject.settingsに保存する所属ターゲット名。種類等はそのTargetが持つ。

再提案：project.settings.reloadは所属Target設定まで整合させ、同じターゲットのオブジェクト参照を維持する。削除されたTarget参照は無効を明示する。target.settings.reloadは個別設定だけを読み直す。検証完了後に反映し、CMakeは再生成しない。外部で変更された設定を保存時に黙って上書きしない。

確認済み：Target側にsettings.get()／save(values)／reload()を用意する。project.set_target_settings(name, values)は設けず、project.get_target(name).settings.save(values)を使う。set_source_directoriesも専用メソッドは設けず、設定データの項目を変更してsaveする。open後の再指定は不要。Project側のsettings.get／save／reload、set_build_profile、project.infoは確認済みの構成を維持する。設定データの具体的な項目・型名は実装時に整理する。保存範囲・再読み込み時のオブジェクト参照維持等の詳細案まで、このAPI構成の合意で確定したとはしない。

### プロジェクト設定の実装時に考慮する事項

設定クラスを実装する際は、C++規格（C++17／20など）や成果物（実行ファイル・ライブラリ等）の出力先などを、設定データの項目として考慮する。こうした項目ごとに専用APIを定義・確認するのではなく、既存のsettingsの取得・保存の仕組みで扱う。具体的なフィールド・型・配置・既定値・検証は設定クラスの実装時に整理する。

その他の候補とCMakeの対応機能は[PROJECT_SETTINGS_RESEARCH.md](../references/PROJECT_SETTINGS_RESEARCH.md)を参考にする。調査候補全体の採用を確定するものではない。

### 対応種類（データ形式は再提案）

確認済み：利用側のターゲット種類は静的ライブラリ・共有ライブラリ・実行ファイル・ヘッダーオンリー・テストとする。列挙名の案は `STATIC_LIBRARY`、`SHARED_LIBRARY`、`EXECUTABLE`、`HEADER_ONLY`、`TEST`。`TEST` はテスト構成のフォーマットをある程度揃えるための独立した種類として提供する。「EXECUTABLEと別のテスト設定だけで表す」という提案は採用しない。内部でどのCMake処理を組み合わせるかと、利用側の種類の区分は分けて扱う。

    TargetType.STATIC_LIBRARY,

## ジャンル5：CMake更新

確認済み：公開APIはproject.update(options=None)とtarget.update(options=None)。Project全体または対象Targetの設定・ファイル変更を反映する。公開走査APIは不要。

```python
report = project.update()
report = target.update()
```

確認済み：project.updateは通常引数なしで保存済み設定を使う。今回だけ変更する場合は任意のoptionsで指定する。保存済み構成名や今回限りの構成データもoptionsで指定でき、省略時は既定構成を使う。optionsの具体的な型・項目・上書き規則は実装時に整理する。登録・専用ファイル作成を実行の前提にしない。走査・CMake入力更新・再生成を行い、コンパイルしない。外部のファイル変更、設定変更、自動更新OFFの変更を反映する。ファイル操作の自動更新は操作したTargetの更新処理を使う。

追加確認済み：target.update(options=None)を用意する。通常は引数なしで保存済み設定を使い、今回限りの変更はoptionsで指定する。対象Targetの設定・ファイル変更を反映し、コンパイルは行わない。結果はUpdateReportで返す。確認済み：ターゲットごとにビルド用のCMakeを持ち、target.updateは対象Targetのビルド用CMakeを使って更新する。対象Targetの保存済み設定を読み直して検証し、ファイル配置の走査と当該CMake入力の更新・再生成を行う。CMakeファイルの具体的な配置や依存関係の反映方法は実装時に整理する。

最新の確認済み方針：`project.update()` は保存済みのプロジェクト設定と所属ターゲット設定を自動で再読み込み・検証してから、ファイル配置の走査、CMake入力の更新、再生成を行う。設定やファイルを外部で変更した場合も、利用側はupdateだけで反映できる。以前の「updateは読み直さず、先にsettings.reloadを要求する」方針は撤回する。

ファイル操作からの自動更新は対象Targetの更新処理を使い、その設定を再読み込みする。settings.getで取得して編集しただけのコピーは保存対象にならず、updateにも反映されない。設定変更を反映するにはsettings.saveで保存しておく。設定の再読み込み・検証に失敗した場合はCMake更新へ進まず、失敗を返す。ファイル操作が既に完了していれば、その完了部分もFileOperationReport等で伝える。

settings.reloadは設定のみを読み直したい場合のAPIとして維持する。updateの戻り値は成功可否・変更内容・CMake実行結果を含むUpdateReport。失敗時に未反映状態を保持する詳細は引き続き設計する。

以下の一組を確認済み。link_projectは単数名・第2引数の種類指定を維持し、第1引数を相手の設定用ディレクトリとする。同一プロジェクト内のリンクには別用途のlink_targetを追加する。

| --- | --- |
| target.settings.link_project(config_directory, link_type) | 他プロジェクトのmain_targetを指定種類でリンク |
| target.settings.link_target(other_target, link_type) | 同じProjectに所属するTargetオブジェクトを指定種類でリンク |

各linkは1回に1つのリンク先を登録し、結果に解除用のdependency_idを含める。登録・解除は設定を保存し、update/buildでCMakeへ反映する。結果型の詳細や外部依存の引数データは実装時に整理する。外部依存ではパッケージ名や場所に加えてリンク先ターゲット等を指定する案。解除時の条件は以下の確認済み方針を維持する。

### 外部依存の解除の条件

確認済み：外部パッケージ・CMakeソース・ビルド済みライブラリの対応は、リンク登録を解除できることを条件とする。最新の補足により、ヘッダーのインクルードパス等の付随設定が残ることは許容する。登録前の状態へ完全に復元することは必須ではない。解除したライブラリへのリンクや、それを必要とする取り込みが残ってビルドを妨げないことを重視する。

この条件を満たすための設計案：

- 各リンク登録に依存IDを付け、依存本体の取り込みと利用側ごとのリンクを区別して管理する。登録由来のヘッダー参照先・定義・構成別ライブラリパス等を追跡できるようにする。
- unlinkは対象のリンク登録を除く。登録由来の付随設定を可能な範囲で整理するが、インクルードパス等の残留は許容し、完全除去は必須にしない。同じ設定を他の依存が必要とする場合や利用側が独立に指定している場合は残す。不要なリンク指定や必須の取り込みが残り、解除した依存の不在で失敗する状態にはしない。
- 複数ターゲットから利用中の依存の取り込みは、最後の参照を解除するまで維持する。依存IDや参照は保存し、Projectを開き直した後も解除可能にする。
- 次のupdateで保存設定からCMake入力を再生成し、不要になったパッケージ取り込み・ソース組み込み・インポート定義を除く。手作業のCMake記述を推測で削除する方式にはしない。
- 外部パッケージのアンインストール、依存先ソースやビルド済みライブラリの削除は行わない。再生成失敗は成功扱いにせず、設定解除済みか・CMakeへ未反映かを区別して返す。

リンク解除も設定変更後にupdate/buildで反映することを確認済み。結果型の詳細、CMakeキャッシュや外部CMake処理が作る副作用の取り扱いは実装時に整理する。ビルドディレクトリの無条件削除を解決策にしない。

- `gtest_discover_tests` でビルドした実行ファイルからケースを列挙しCTestへ登録できる。ケース単位の結果取得やパラメーター化テストにも対応する。テスト一覧の確定には実行ファイルが必要で、updateだけで常に取得できるとはしない。[CMake GoogleTestモジュール](https://cmake.org/cmake/help/latest/module/GoogleTest.html)

- 結果はCTestのJUnit XML等を内部で読みTestReportへ変換する案。JUnit出力はCMake 3.21以降の機能なので、採用時は最低バージョンを合わせる。以前のレポートを今回の結果と誤認しないよう操作ごとに管理し、結果取得不能も診断する。[CTestのJUnit出力](https://cmake.org/cmake/help/latest/manual/ctest.1.html#cmdoption-ctest-output-junit)
- GoogleTestの依存は複数のTESTターゲットで共有する。取得方法（既存パッケージ・ソース取得等）、Windowsのランタイム整合、依存版の固定は実装時に設計する。GoogleTest採用を自動ダウンロードの確定とは扱わない。

- saveは設定を検証・保存して管理オブジェクトへ反映する。不正な設定はエラーとし、保存失敗時にメモリ上だけ新設定へ切り替えない。CMake反映は更新・ビルド時に行う。
- reloadは保存済み設定を読み直す。CMake再生成・ビルドは行わない。ProjectとTargetの再読み込みの範囲・既存オブジェクト参照の扱いは再提案を確認する。
- 設定データの具体的な型と保存範囲、戻り値の詳細はProject・Target分離に合わせて整理する。全ターゲットの詳細をProject側のsaveで上書きすることを既定要件にしない。
- project.infoは設定に加えて認識済みファイル・取得済み成果物・更新やビルドの状態等の保持情報もまとめて返す用途で残す。取得のための走査・CMake実行は行わない。未取得・古い情報を区別する詳細項目は今後設計する。settings.getは設定値のコピー取得として維持し、表示・出力は利用側が行う。
- 独立した復元APIは設けない。設定APIは今後の設計に応じた変更を許容する。
